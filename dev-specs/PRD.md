# PRD: Scalp Assist

**Версия документа:** 2.0  
**Актуальность:** 17 октября 2026 г.  
**Статус продукта:** четыре аналитических раздела реализованы в репозитории;
production-развёртывание требует согласования frontend hosting и HTTPS с
текущим кодом.

## 1. Назначение и границы

Scalp Assist — персональный self-hosted веб-сервис для исследования рынка
бессрочных фьючерсов. Он объединяет скринер, наблюдение за prop list,
межбиржевой арбитраж и свечные графики в интерфейсе с общей авторизацией.

Продукт предоставляет справочную рыночную информацию для последующего ручного
анализа. Он не открывает сделки, не отправляет ордера, не хранит торговые ключи
пользователя и не заявляет, что расчётный spread можно исполнить с прибылью.

Этот документ описывает текущую продуктовую версию и критерии её развития.
Реализация проверена по исходникам репозитория; заявления о production-работе
сервиса должны подтверждаться отдельной эксплуатационной приёмкой.

## 2. Пользователь и цели

### Целевой пользователь

Один владелец сервиса, который самостоятельно просматривает кандидатов для
скальпинга, список монет проп-компаний, различия цен между биржами и графики.
Публичной регистрации, ролей и разделения данных по аккаунтам в текущей версии
нет.

### Цели

| Цель | Ожидаемый результат |
|---|---|
| Быстро выбирать инструменты | Актуальный ранжированный top скринера и история снимков |
| Следить за prop list | Видеть доступные контракты, источник, 24h change/turnover и BTC correlation |
| Наблюдать межбиржевые цены | Сравнивать направления, расчётный spread, комиссии, funding и видимую top-level capacity |
| Сократить повторные запросы | Использовать общие клиенты, TTL-кэши и объединение одновременных fetch |
| Переживать частичный отказ | Показывать состояние бирж и продолжать работу в допустимом degraded mode |
| Защитить рабочие экраны | Требовать вход для приватного UI и защищённых API |

## 3. Пользовательские сценарии

1. Владелец входит и открывает `/app`, чтобы оценить состояние контуров.
2. На `/app/screener` смотрит top-N, раскрывает метрики, открывает историю,
   настраивает пороги и импортирует монеты из TXT.
3. На `/app/prop-screen` фильтрует prop-монеты по поиску, суточному движению и
   обороту, учитывая выбранную биржу-источник и корреляцию с BTC.
4. На `/app/arbitrage` проверяет, на каких биржах доступны совпадающие
   контракты, изучает направление buy/sell, комиссии, gross/net и funding.
   Ссылки ведут к графикам сравнительных цен и Gross.
5. На `/app/charts` поддерживает личную сетку инструментов; изменение сетки
   возможно также кнопкой `Set charts` в таблицах скринера и prop screen.

## 4. Продуктовые разделы и требования

### 4.1. Скринер

- Источники: Binance USDⓈ-M и Bybit linear, только публичные данные.
- Быстрый цикл по умолчанию — 15 минут; медленный цикл корреляции — 2 часа.
- Поддерживаются USDT/USDC-контракты, нормализация base и multiplier,
  blacklist и ручные overrides. Разные множители одного base считаются разными
  инструментами.
- Метрики включают оборот (суммарно по биржам), процент изменения, дневной
  диапазон, funding, relative tick, inplay, корреляцию с BTC и score.
- Если Binance доступен для инструмента, он основной для ценовых метрик;
  Bybit покрывает Bybit-only инструмент. Отказ одного источника не блокирует
  быстрый цикл при успешном ответе второго.
- Жёсткие фильтры и веса score настраиваются через страницу настроек/API.
  Текущие значения сохраняются отдельно от исторических снимков.
- Результат ограничивается `top_n`; список снимков, история инструмента и
  агрегированная статистика сохраняются в SQLite.
- Prop list редактируется через UI; TXT импорт разбирает запятые и переносы
  строк, нормализует регистр и объединяет ввод с существующим списком.

### 4.2. Prop screen

- Использует ту же prop list, что и скринер; новый список и отдельная таблица БД
  не создаются.
- Цикл обновления по умолчанию — одна минута. Сервис получает каталоги и 24h
  tickers Binance/Bybit без загрузки funding/BBO для этого контура.
- Показываются только подходящие активные линейные perpetual-контракты с
  USDT/USDC; внутри биржи USDT предпочтительнее USDC.
- Сначала сопоставляется точная пара base+multiplier. Для x1 допускается
  безопасный fallback к единственному доступному multiplier при отсутствии
  отдельной prop-записи; при неоднозначности инструмент пропускается.
- Binance приоритетен для change/turnover; валидный Bybit используется как
  fallback. Источник и статусы бирж видны пользователю.
- Последний run хранится в памяти и пересчитывается после изменения списка;
  отдельная история prop screen не ведётся.
- Таблица поддерживает поиск, сортировку и минимальные пороги 24h change и
  turnover. Корреляция часовых доходностей с BTC за 7 дней читается из общего
  кэша и обновляется медленным циклом.

### 4.3. Арбитраж

- Источники: Binance, Bybit и OKX. Сравниваются только активные линейные
  бессрочные USDT-контракты с одинаковой идентичностью
  `base + quote + multiplier + kind`.
- Все направленные пары проверяются отдельно: покупка по ask на одной бирже,
  продажа по bid на другой.
- Основные показатели:

  ```text
  gross_bps = (sell_bid / buy_ask - 1) * 10000
  net_TT_bps = gross_bps - taker_fee_buy_bps - taker_fee_sell_bps
  net_MT_bps = gross_bps - maker_fee_buy_bps - taker_fee_sell_bps
  capacity_usd = min(buy_ask * ask_qty * qty_multiplier,
                     sell_bid * bid_qty * qty_multiplier)
  ```

- Net T/T является базой фильтрации, сортировки и статистики. Net M/T —
  дополнительный сценарий с maker на стороне покупки; исполнение maker не
  гарантируется.
- Funding edge нормализуется к часу и показывается отдельно от spread. Он не
  включается в Net без модели срока удержания и фактических funding times.
- Котировки должны иметь положительные валидные bid/ask, быть свежими и иметь
  допустимый межбиржевой временной skew. Действуют sanity-границы gross,
  минимумы net и capacity.
- Сканирование стартует сразу и повторяется по умолчанию раз в 10 секунд.
  Refresh защищён от параллельного запуска. Результаты сохраняются в SQLite не
  чаще раза в минуту по умолчанию; срок хранения — 30 дней.
- При доступности двух бирж допускается degraded scan; при нуле или одной
  успешной бирже сохраняются статусы источников, полноценный run невозможен.
- Экран List поддерживает поиск, статусы, маршрут, исходные символы, цену,
  spread, capacity, funding edge и время `first_seen_at`. Обзор показывает
  короткий список положительных Net T/T и общее число.
- Вкладка Charts сравнивает close Binance/Bybit/OKX и ряд Gross для 1m/5m;
  вкладка Info показывает заданные комиссии. Вкладка Settings пока является
  резервом.
- Комиссии и пороги берутся из YAML и применяются при старте процесса.

### 4.4. Свечные Charts

- Отдельная от арбитражной аналитики страница `/app/charts` показывает до 10
  OHLC-графиков в двухколоночной сетке.
- Интервалы: `5m` и `1h`; история загружается через REST, обновления свечей
  доставляются через WebSocket.
- Допускаются активные linear perpetual-контракты. Binance предпочтительна;
  при отсутствии подходит Bybit. Внутри биржи выбирается USDT, затем USDC.
- Раскладка, порядок и интервалы сохраняются в localStorage под ключом
  `scalpAssist.chartGrid.v1`. Дубли слотов допустимы, максимальное число — 10.
- `Set charts` синхронизирует выбор в скринере и prop screen; соседние вкладки
  уведомляются через `storage` event и применяют изменения по команде UI.

## 5. Навигация и интерфейс

- `/` — публичная страница;
- `/auth` — вход;
- `/app` — приватная сводка;
- `/app/screener`, `/app/screener/history`, `/app/screener/settings`,
  `/app/screener/wiki` — скринер;
- `/app/prop-screen`, `/app/prop-screen/wiki` — prop screen;
- `/app/charts` — пользовательская сетка свечей;
- `/app/arbitrage`, `/app/arbitrage/charts`, `/app/arbitrage/info`,
  `/app/arbitrage/settings`, `/app/arbitrage/wiki` — арбитраж.

Старые `/app/top`, `/app/history`, `/app/settings` сохраняются для совместимости.
При истечении сессии UI направляет пользователя на `/auth`; после выхода — на
`/`. Интерфейс имеет светлую/тёмную тему и адаптивную компоновку.

## 6. API и сессии

API размещает backend. `/api/health` и `POST /api/auth/login` доступны без
сессии. Остальные API защищены общей авторизацией.

Ключевые группы маршрутов:

- Auth: `/api/auth/login`, `/api/auth/logout`, `/api/auth/me`;
- Screener: `/api/screener/top`, `/history`, `/snapshots`, `/stats`,
  `/prop-list`, `/settings`, `/refresh`;
- Prop screen: `/api/prop-screen`, `/api/prop-screen/refresh`;
- Arbitrage: `/api/arbitrage/opportunities`, `/stats`, `/refresh`, `/fees`,
  `/charts/instruments`, `/charts/stream`;
- Charts: `/api/charts/instruments`, `/api/charts/stream`;
- Overview: `/api/dashboard/summary`.

Для совместимости оставлены старые API-маршруты скринера без namespace.
Сессия передаётся в HttpOnly cookie; пароли хранятся в виде bcrypt-хэшей.
Первичный аккаунт создаётся из `auth.bootstrap_*` при первом старте с пустой БД.

## 7. Архитектура и данные

- Backend: Go 1.22+, стандартный `net/http`, structured logging `slog`.
- Frontend: React 19, Vite, Lightweight Charts.
- Хранилище: SQLite (`modernc.org/sqlite`), встроенные SQL-миграции и WAL.
- Сетевые клиенты Binance/Bybit создаются в точке запуска и переиспользуются
  сервисами. OKX подключена к арбитражу.
- Каталоги контрактов кэшируются долго, рыночные тикеры/BBO — коротко; одинаковые
  параллельные cache misses объединяются.
- Данные скринера, пользователи, настройки и prop list хранятся в SQLite.
  Арбитражные наблюдения хранятся в SQLite с retention. Текущее состояние
  prop-screen — в памяти; состояние пользовательской сетки — в браузере.
- Конфигурация читается из YAML. Интервалы задаются в `cycles`; параметры
  скринера могут иметь сохранённые runtime overrides. Настройки арбитража
  требуют перезапуска.

## 8. Нефункциональные требования

### Надёжность и отказ источников

- Сетевые ошибки и состояние каждой биржи должны быть различимы в run/status.
- Частичный отказ одного источника не должен обрушать доступные режимы скринера
  и prop screen; арбитраж продолжает сканирование при наличии хотя бы двух
  бирж.
- Нельзя сохранять новый успешный снимок скринера, если недоступны обе биржи.
- Повторные ручные refresh не должны запускать параллельные конкурентные scan.
- SQLite миграции должны применяться автоматически и сохранять совместимость с
  имеющимися данными.

### Безопасность

- Не подключать приватные торговые API и не принимать ключи для исполнения.
- Защищать приватные API общей авторизацией и ограничивать попытки входа.
- Не сохранять пароль в открытом виде. Секреты и локальная БД не должны
  попадать в Git.
- В production весь UI/API-трафик должен передаваться по HTTPS. Текущая
  реализация запуска сервера и раздачи frontend пока не покрывает это требование
  end-to-end; до включения production-развёртывания оно является блокером.

### Производительность и свежесть

- Не запрашивать полный market payload отдельно каждым контуром при наличии
  пригодного кэша.
- Объединять одинаковые конкурентные запросы и WebSocket-подписки.
- Показывать время данных и состояния источников, чтобы пользователь мог
  оценить их актуальность.
- Соблюдать TTL, rate limits и ограничения публичных API бирж.

## 9. Ограничения текущей версии

- Арбитраж использует REST BBO первого уровня, а не потоковый BBO и полный
  стакан; не моделирует slippage, latency, funding holding period, transfer,
  правила округления и индивидуальный VIP fee tier.
- Показанная capacity не гарантирует, что такой размер исполним целиком.
- Funding разных бирж имеет разную семантику и интервалы; edge — оценочная
  часовая метрика.
- Prop screen не сохраняет собственную историю.
- Настройки арбитража не редактируются из UI; уведомления не реализованы.
- VPS-инструкция в `specs/Deploy_VPS_guide.md` ссылается на отсутствующее сейчас
  в backend встраивание `web/dist`/HTTPS. Её команды нельзя считать рабочим
  подтверждённым production-рецептом до исправления и smoke-проверки.

## 10. Вне текущего объёма

- Автоматическое или полуавтоматическое исполнение сделок.
- Торговые API-ключи, аккаунтные балансы, позиции и управление риском.
- Spot/perpetual и межсетевой арбитраж.
- Регистрация пользователей, роли и многопользовательские данные.
- Уведомления Telegram и внешние каналы оповещения.
- Сигналы «купить/продать» и гарантии доходности.

## 11. Приоритеты последующего развития

В плане проекта эти задачи помечены как будущие; они не входят в статус
выполненных этапов:

1. WebSocket BBO для арбитражных котировок с REST bootstrap/fallback,
   переподключением и контролем возраста/последовательности данных.
2. Догрузка глубины для выбранных кандидатов и расчёт capacity/slippage для
   заданного размера позиции.
3. Аналитика сохранённых наблюдений: длительность маршрута, медианы/квантили,
   доступность, графики spread и экспорт CSV.
4. Редактирование порогов и персональных комиссий в UI с валидацией и
   сохранением настроек.
5. Уведомления без автоматического исполнения.
6. Согласование и реализация production-схемы: раздача frontend, HTTPS,
   обновление бинарника/ассетов, backup/restore и smoke-проверки.

## 12. Критерии приёмки

### Функциональная приёмка

- Успешный вход открывает `/app`; logout закрывает приватную сессию.
- Все четыре раздела доступны из интерфейса, приватные API без сессии
  возвращают отказ.
- Скринер отображает top/history/settings, prop flags и результат TXT-импорта.
- Prop screen применяет приоритет Binance и корректный Bybit fallback, не
  показывает неподтверждённые сопоставления multiplier.
- Арбитраж проверяет fresh/stale/skew, контрактную identity, комиссии,
  capacity и допускает degraded scan при двух биржах.
- Charts ограничивает сетку десятью слотами, переживает перезагрузку браузера,
  использует правильный источник и корректно подписывает/отписывает WebSocket.
- История скринера и sampled history арбитража переживают перезапуск процесса.

### Инженерная приёмка изменений

- Изменение в доменной модели синхронизировано с расчётом, storage, API, UI и
  fixture/unit тестами.
- Обычные тесты не требуют внешней сети; live-smoke отделён и выполняется по
  локальным правилам окружения владельца.
- Перед релизом должны проходить `go test ./...`, сборка Go, frontend tests и
  `npm run build`.

### Production-приёмка

- Схема хостинга явно раздаёт frontend и API по HTTPS; маршрутизация `/api/*`,
  WebSocket upgrade и SPA fallback проверены.
- Проверены вход, cookie, `/api/health`, закрытые API, миграции и backup/restore.
- После запуска наблюдаются циклы, ошибки источников, память и рост SQLite;
  проектный критерий — 48 часов без неконтролируемых сбоев.
