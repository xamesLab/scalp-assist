# Scalp Assist — сводка проекта

**Актуализировано:** 17 октября 2026 г.  
**Назначение:** единый обзор продукта, выполненной разработки и фактического состояния репозитория.

## 1. Что представляет собой проект

Scalp Assist — персональный веб-сервис для наблюдения за рынком бессрочных
фьючерсов. Он собирает публичные рыночные данные Binance, Bybit и OKX и
предоставляет несколько аналитических разделов под общей авторизацией.

Система предназначена для подготовки ручного анализа. Она не использует
торговые ключи, не отправляет и не управляет ордерами и не обещает, что
показанная возможность исполнима или прибыльна.

## 2. Текущее состояние продукта

В коде реализованы четыре пользовательских раздела:

1. **Скринер** Binance USDⓈ-M и Bybit linear: нормализация инструментов,
   фильтрация, метрики, скоринг, top-N, история, статистика и настройки.
2. **Prop screen**: доступные на Binance/Bybit инструменты из общей prop list,
   метрики за 24 часа, поиск и сортировка.
3. **Арбитраж** Binance/Bybit/OKX: сравнение одинаковых линейных бессрочных
   USDT-контрактов, направленный gross/net spread, комиссии, top-of-book
   capacity, funding edge и sampled history.
4. **Charts**: личная для браузера сетка до десяти OHLC-графиков Binance/Bybit
   с интервалами 5 минут и 1 час. Отдельно реализованы сравнительные графики
   арбитража для общих инструментов трёх бирж.

Общий экран `/app` содержит краткую сводку контуров. Публичные страницы — `/` и
`/auth`; рабочие экраны находятся под `/app/*`.

## 4. Архитектура и структура реализации

Приложение организовано как один Go backend и React SPA. Обменные клиенты,
нормализация контрактов и кэш рыночных ответов общие для соответствующих
контуров. SQLite — основное постоянное хранилище.

```text
Binance ─┐
Bybit ───┼─ exchange clients + normalization + market data cache
OKX ────┘                   │
             ┌──────────────┼──────────────┐
          screener       prop-screen    arbitrage
             └──────────────┼──────────────┘
                       SQLite + API
                            │
                         React SPA
```

Основные каталоги:

- `cmd/screener` — запуск серверного процесса;
- `internal/exchange` — клиенты бирж;
- `internal/marketdata`, `internal/normalize`, `internal/domain` — общие модели,
  кэш и идентичность инструментов;
- `internal/metrics`, `internal/scoring`, `internal/corr`,
  `internal/scheduler` — скринер;
- `internal/propscreen` — prop screen;
- `internal/arbitrage` — расчёт и сервис арбитража;
- `internal/charts` — каталог и поток свечей отдельного Charts;
- `internal/store` — SQLite и встроенные миграции;
- `internal/api` — HTTP/WebSocket API и авторизация;
- `web` — React/Vite frontend.

## 5. Основные правила продукта и расчётов

- Используются публичные биржевые market endpoints; приватные торговые API не
  входят в продукт.
- Идентичность инструмента включает базовый актив и множитель. Для арбитража
  также важны quote и тип контракта. Контракты с разными множителями нельзя
  считать одним инструментом.
- Binance приоритетен для ценовых метрик скринера и prop screen; Bybit покрывает
  собственные листинги и используется как fallback.
- Пропуск одной биржи должен отражаться как деградация. Скринер и prop screen
  могут продолжить работу на оставшейся бирже; арбитражу нужны минимум две.
- Сетевые запросы и совпадающие WebSocket-подписки по возможности разделяются
  между контурами/клиентами через общие кэши и hub.
- Спред арбитража считается по buy ask и sell bid. Net T/T учитывает заданные
  taker-комиссии; Net M/T показывается как отдельный сценарий комиссии. Funding
  отображается отдельно. Capacity оценивается только по первому уровню BBO.
- Пользовательская сетка Charts хранится в браузере под ключом
  `scalpAssist.chartGrid.v1`, а не в серверной БД.

## 6. Известные ограничения и незавершённая приёмка

1. Арбитраж получает BBO через REST и оценивает только первый уровень. Нет
   моделирования slippage, глубины стакана, задержки и ограничений конкретного
   ордера; показанные значения не являются исполнимой котировкой.
2. История арбитража сохраняет sampled runs, а не каждый быстрый scan. Статистика
   описывает сохранённые наблюдения.
3. Арбитражные комиссии и пороги задаются YAML и требуют перезапуска; отдельная
   вкладка Settings пока зарезервирована.
4. Список prop-монет хранится в SQLite. Файл `prop-list.txt` в корне — исходный
   список для ручного TXT-импорта в настройках скринера, не автозагрузка при
   старте сервера.
5. Production-часть документации и код расходятся. VPS-инструкция утверждает,
   что React зашит в Go-бинарник и описывает HTTPS/autocert. В текущем исходном
   коде `main.go` запускает API на `dev_http`; frontend собирается отдельно, а
   HTTP handler не раздаёт `web/dist`. Следовательно, единый production-бинарник
   и end-to-end HTTPS-деплой нельзя считать подтверждёнными функциями текущей
   версии. Перед реальным деплоем эти документы и реализацию нужно согласовать.
6. В плане этапы 17–20 остаются следующими идеями, а не выполненными работами:
   WebSocket BBO для движка арбитража, глубокая ликвидность/slippage, расширенная
   аналитика исторических spread, UI настроек и уведомления.
