## 1. Обзор

### 1.1. Суть продукта

Персональный селфхостед веб-сервис для фьючерсного скальпера. Автоматически, круглосуточно сканирует фьючерсные инструменты Binance и Bybit, применяет формализованные правила отбора (методичка RDNSCALO + скоринг), ведёт историю и показывает в веб-интерфейсе текущий топ-20 кандидатов для торговли с пометками: входит ли инструмент в список проп-компании, коррелирует ли с BTC, движется ли самостоятельно относительно рынка.

Система информационная: доводит отбор до состояния «вот кандидаты — иди смотри графики». Поиск формаций, оценка уровней и торговые решения остаются за пользователем.

### 1.2. Пользователь

Один пользователь — владелец. Скальпер на Binance/Bybit + проп-компания с ограниченным списком инструментов. Свой VPS, технически грамотен.

### 1.3. Скоуп MVP / вне скоупа

**MVP:** Go-скринер (два цикла: быстрый — метрики, медленный — корреляция) + SQLite + REST API + React-фронт (3 страницы), редактирование правил отбора из UI, один бинарник, деплой systemd без контейнеров, публичный HTTPS (встроенный autocert) + авторизация email/пароль с JWT.

**Пост-MVP (каркас закладывается, реализация позже):** Hermes Agent + Telegram-рассылка 2×/день (эндпоинт `format=text` делается в MVP как задел); OKX как третий источник; ΔOI и ATR; предпросмотр «как изменится топ» при правке настроек до их сохранения.

**Не делаем вообще:** автоторговлю, торговые ключи бирж, сигналы «покупай/продавай», Docker, realtime-стриминг. Мультипользовательность и самостоятельная регистрация — не в MVP, но авторизация и таблица `users` спроектированы так, чтобы SaaS-расширение не требовало переделки (см. 4.9).

## 3. Архитектура

```
[Binance Futures API]      [Bybit v5 API]
        \                      /
         v                    v
  ┌────────────────────────────────────┐
  │ Go-бинарник (единственный процесс) │
  │  scheduler: быстрый цикл (15 мин)  │
  │             медленный цикл (2 ч)   │
  │  exchange → normalize → metrics    │
  │  → scoring → store (SQLite, WAL)   │
  │  api: REST · embed: React-статика  │
  └──────────────┬─────────────────────┘
                 │ HTTPS :443 (autocert) · JWT-auth
             браузер (десктоп/телефон)
```

| Решение | Выбор | Обоснование |
|---|---|---|
| Бэкенд | Go 1.22+, stdlib `net/http`, `log/slog` | Роутер stdlib умеет методы/параметры; без внешних зависимостей |
| БД | SQLite через `modernc.org/sqlite` | Pure Go → CGO_ENABLED=0, кросс-компиляция, один статический бинарник; подтверждён в проде |
| Режим SQLite | WAL, synchronous=NORMAL, busy_timeout=5000; два пула: writer MaxOpenConns(1) + reader | Стандартная практика драйвера против SQLITE_BUSY |
| Фронт | React + Vite, статика в `go:embed` | Один артефакт деплоя |
| Деплой | scp бинарника + systemd (Restart=always), публичный HTTPS на :443 | Без контейнеров; TLS — встроенный autocert (Let's Encrypt), нужен только домен |
| Авторизация | email+пароль (bcrypt) → JWT в HttpOnly-cookie | Один пользователь в MVP; таблица `users` и middleware готовы к SaaS (см. 4.9) |
| Данные бирж | Только публичные эндпоинты, без ключей | Система физически не может торговать |

Ограничение драйвера: версия `modernc.org/libc` в go.mod фиксируется точно по go.mod самого `modernc.org/sqlite`.

## 4. Функциональные требования

### 4.1. Сбор данных

**FR-1. Быстрый цикл (каждые 15 мин, конфигурируемо):**
- Binance USDⓈ-M: `exchangeInfo` (кэш 24 ч), `ticker/24hr`, `premiumIndex`;
- Bybit v5 linear: `instruments-info` (обязательно cursor-пагинация — символов >500), `tickers`.
- Таймауты, retry с backoff, чтение rate-limit заголовков (Binance: X-MBX-USED-WEIGHT-1M, бюджет 2400/мин; Bybit: X-Bapi-Limit-*, retCode 10006).
- Отказоустойчивость: недоступность одной биржи не прерывает цикл — снапшот по живой бирже, деградация в `/api/health`.

**FR-2. Медленный цикл (каждые 2 ч, конфигурируемо):** 1h-свечи за 7 дней (168 шт.) по каждому инструменту + BTCUSDT каждой биржи → корреляция → кэш `corr_cache`. Пачки по 50 символов с паузами; бюджет: klines weight 2 × ~600 символов ≈ 1200 из 2400/мин — проходит с запасом.

### 4.2. Нормализация (FR-3)

Единый инструмент = базовый актив + множитель: `1000PEPEUSDT` (BN) ≡ `PEPEUSDT`×1000-нотация (BB) → `{PEPE, ×1000}`. Флаги `on_binance`, `on_bybit`; производный флаг **`bybit_only`** (методичка: листинги/монеты, которых нет на Binance — отдельный интерес). Стейбл-пары отсеиваются. Неизвестный паттерн символа → warning в лог. Коллизии — таблица исключений в конфиге.

### 4.3. Метрики (FR-4)

| Метрика | Источник | Примечание |
|---|---|---|
| Оборот 24ч, $ | ticker | сумма по биржам инструмента |
| Диапазон дня (high−low)/low, % | ticker | основная «шевелёнка» |
| Изменение 24ч, % | ticker | для правила 20% и инплея |
| Funding rate | premiumIndex / tickers | |
| Относительный tickSize, % | exchangeInfo / instruments-info | стоимость тика |
| **btc_corr_7d** ∈ [−1..1] или null | klines (медленный цикл) | Пирсон по часовым доходностям, 7 дней; null при <100 валидных точек (свежий листинг); флаг `high_corr = corr > 0.8` (порог в конфиге) |
| **is_inplay** (bool) | ticker + медиана рынка | самостоятельность движения: Δ инструмента ≥ k× медианы растущего рынка ИЛИ падение при растущей медиане (дефолт: рынок > +3%, k = 2) |
| in_prop_list (bool) | таблица prop_instruments | |
| bybit_only (bool) | нормализация | |

**Приоритет данных (FR-4a):** Binance — основной источник. Если инструмент торгуется на обеих биржах, ценовые метрики (Δ24ч, диапазон дня, funding, tickSize) берутся из данных Binance; данные Bybit используются для суммирования оборота и как единственный источник для инструментов, которых на Binance нет. Корреляция считается по свечам Binance при наличии инструмента там, иначе по Bybit.

Расчёт корреляции: доходности `r[i]=close[i]/close[i−1]−1`, ряды монеты и BTC выравниваются по open time (непарные точки отбрасываются в обеих сериях), BTC берётся той же биржи.

### 4.4. Фильтры и скоринг (FR-5)

Жёсткие фильтры (порядок применения): статус Trading → не стейбл → не blacklist → `оборот ≥ min_volume_usd` (дефолт $100M, калибруется) → опционально `|Δ24h| ≥ min_change_pct` (дефолт 20%, включаемый флагом; при выключении ранжирование только по score — иначе в тихие дни топ пуст).

Скоринг: перцентильная нормировка по текущей выборке; `score = w_vola·волатильность + w_turn·оборот + w_inplay·инплей − w_corr·corr`; веса в конфиге (дефолт 0.4/0.3/0.2/0.1). Высокая корреляция **не исключает** инструмент жёстко: если `is_inplay=true`, штраф за corr не применяется (исключение методички — монета живёт своей жизнью прямо сейчас). `high_corr` без инплея — визуальная пометка «ходит за BTC» + штраф в score.

Топ-N (дефолт 20) → снапшот. Все пороги и веса этого раздела — редактируемые в рантайме настройки (см. 4.8).

### 4.5. Хранилище (FR-6)

Таблицы: `instruments` (base, multiplier, символы и флаги бирж), `prop_instruments` (instrument_id, note), `snapshots` (id, created_at), `snapshot_rows` (snapshot_id, instrument_id, exchange-набор, все метрики из 4.3, score, rank, in_prop_list, is_inplay, btc_corr_7d), `corr_cache` (instrument_id, corr, updated_at), `settings` (key, value, updated_at — рантайм-оверрайды правил отбора поверх YAML-дефолтов, см. 4.8), `users` (id, email UNIQUE, password_hash bcrypt, created_at — см. 4.9). Миграции — нумерованные .sql в go:embed, идемпотентный запуск. Ретеншн: хранить всё (объёмы ничтожны).

### 4.6. REST API (FR-7)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/top?limit=20` | текущий топ, все метрики и флаги |
| GET | `/api/top?format=text` | предформатированный текст (задел под пост-MVP агента) |
| GET | `/api/history?symbol=&days=` | история метрик/рангов инструмента |
| GET | `/api/snapshots?from=&to=` | снапшоты за период (для «Истории») |
| GET | `/api/stats?days=` | частотность попаданий, средняя доля пропа, новички периода |
| GET / PUT | `/api/prop-list` | чтение/замена проп-листа |
| GET / PUT | `/api/settings` | чтение/изменение правил отбора (пороги, веса, top_n) с валидацией |
| POST | `/api/refresh` | внеплановый быстрый цикл (mutex от параллельных) |
| GET | `/api/health` | статусы бирж, возраст снапшота и corr-кэша |
| POST | `/api/auth/login` | вход: email+пароль → JWT в HttpOnly-cookie; rate-limit 5 попыток/мин с IP |
| POST | `/api/auth/logout` | выход (очистка cookie) |
| GET | `/api/auth/me` | текущий пользователь (проверка сессии для UI) |

Все `/api/*`, кроме `/api/auth/login` и `/api/health`, защищены JWT-middleware — без валидного токена 401. Единый формат JSON-ошибок; graceful shutdown; CORS только для dev.

### 4.7. Веб-интерфейс (FR-8)

Три страницы. Эталон дизайна — HTML-мокап `Скринер для фьючерсного скальпера/Скринер.dc.html` (самодостаточная вёрстка: IBM Plex Sans/Mono, светлая и тёмная темы через CSS-переменные) и скриншоты в `shots/`. Дизайн переносится в React максимально точно: CSS-переменные, шрифты, цвета бейджей, отступы и структура компонентов берутся из мокапа как есть.
1. **Топ** — статусная строка (биржи, время снапшота), 4 сводные карточки, таблица топ-20 с раскрывающимися строками; управление: «Обновить сейчас», поиск, фильтр биржи, «только проп». Пометки строк: проп (зелёный бейдж), `high_corr` («ходит за BTC»), `is_inplay`, `bybit_only`.
2. **История** — частотность попаданий (бары), инсайт-карточки (утро/вечер, доля пропа, новички), список снапшотов; селектор периода 7/14/30 дней.
3. **Настройки** — редактор проп-листа (добавление/удаление, счётчик покрытия топа); редактор правил отбора: `min_volume_usd`, `min_change_pct` + вкл/выкл этого фильтра, `corr_threshold`, параметры инплея (порог рынка, кратность k), веса скоринга, размер топа. Валидация диапазонов на форме, кнопка «Сбросить к дефолтам» (возврат к значениям YAML), подпись «применится со следующим снапшотом» рядом с кнопкой «Обновить сейчас».

Плюс экран входа (email+пароль, в стилистике мокапа): показывается неавторизованному пользователю; любой ответ API 401 → редирект на него; кнопка выхода в шапке.

Общее: переключатель светлой/тёмной темы (дефолт — системная, выбор приоритетнее); адаптив под телефон (второстепенные колонки уходят в раскрытие строки); состояния пустой БД / ошибки API / деградации биржи.

### 4.8. Настройки правил в рантайме (FR-9)

Эффективная конфигурация = YAML-дефолты + оверрайды из таблицы `settings`. Быстрый цикл читает эффективную конфигурацию в начале каждого прогона — изменения действуют со следующего снапшота, рестарт не нужен. `PUT /api/settings` валидирует диапазоны (объём > 0, `min_change_pct` ≥ 0, corr ∈ [0..1], веса ≥ 0, top_n ∈ [1..100]) и отклоняет невалидный набор целиком (всё или ничего). «Сброс к дефолтам» = удаление оверрайдов. Интервалы циклов, blacklist и исключения нормализации остаются только в YAML (изменение — правка файла + рестарт).

### 4.9. Авторизация и HTTPS (FR-10)

Сервис публикуется в открытый интернет (VPN не требуется), поэтому обязательны TLS и авторизация. Это же — задел под SaaS.

- **HTTPS:** встроенный Let's Encrypt autocert (`golang.org/x/crypto/acme/autocert`): бинарник слушает `:443`, на `:80` — редирект на HTTPS + ACME-challenge. Нужен домен, указывающий на VPS. Кэш сертификатов — в data-каталоге (переживает рестарт). Для локальной разработки — dev-режим plain HTTP на localhost (без домена и авторизация опционально отключаема флагом конфига только в dev).
- **Вход:** email + пароль. Пароль хранится только как bcrypt-хэш в таблице `users`. В MVP один пользователь: учётка создаётся при первом старте из конфига (`auth.bootstrap_email` / `auth.bootstrap_password`, применяется только при пустой таблице; после первого входа пароль из конфига можно удалить). Сброс пароля — запуск `screener -reset-password` (перечитывает bootstrap-значения из конфига). Самостоятельной регистрации нет.
- **Сессия:** JWT (HS256; секрет генерируется при первом старте и сохраняется в data-каталоге — сессии переживают рестарт), срок жизни 30 дней, выдаётся в HttpOnly Secure cookie (SameSite=Lax). Logout = очистка cookie.
- **Защита:** middleware на всех `/api/*`, кроме `/api/auth/login` и `/api/health`; rate-limit логина 5 попыток/мин с IP; статика (SPA) отдаётся без авторизации — данные закрыты на уровне API.
- **Задел под SaaS:** `users` — полноценная таблица, JWT несёт `user_id`; для мультипользовательности останется добавить регистрацию/оплату и скоупинг данных по пользователю.

## 6. Правила отбора (методичка RDNSCALO — трассировка)

| Правило методички | Реализация | Статус |
|---|---|---|
| Binance — основа; Bybit/OKX — листинги и то, чего нет на Binance | Binance+Bybit в MVP, флаг `bybit_only`; OKX — пост-MVP | MVP (частично) |
| Монета должна пройти >20% за день и иметь объёмы | Фильтры `min_change_pct=20` + `min_volume_usd` | MVP |
| Красный крест при недостаточном объёме несмотря на % | Порядок фильтров: объём отсекает независимо от Δ | MVP |
| Монеты, постоянно ходящие за BTC, не рассматривать (даже с объёмом $2–3 млрд) | `btc_corr_7d` + `high_corr` (порог 0.8) → пометка + штраф в score | MVP |

## 9. Критерии приёмки MVP

1. 48 часов непрерывной работы: снапшоты каждые 15 мин без пропусков, corr-кэш обновляется, RAM стабильна.
2. Дашборд открывается с ноутбука и телефона из обычной сети по `https://домен`: сертификат валиден, HTTP редиректит на HTTPS, без логина — экран входа, после логина показывает актуальный топ; тема переключается; «Обновить сейчас» даёт свежий снапшот ≤ 60 с.
3. Санити методички на живом рынке: ни одной монеты ниже порога объёма в топе; SOL/DOGE/XRP-класс помечен `high_corr`; в день общего пампа инплей-флаг выделяет самостоятельные монеты.
4. Проп-лист редактируется из UI, флаги в топе меняются со следующего снапшота.
5. Правила отбора редактируются из UI: изменение порога объёма/процента влияет на следующий снапшот без рестарта; «Сбросить к дефолтам» возвращает значения YAML; невалидные значения отклоняются с понятной ошибкой.
6. Рестарт сервиса и ребут VPS не требуют ручных действий; история и настройки целы.
7. `format=text` возвращает готовый текст топа (задел под агента) — проверка curl'ом с токеном.
8. Авторизация: без cookie все `/api/*` (кроме `/api/health` и `/api/auth/login`) отвечают 401, UI уводит на экран входа; сессия переживает рестарт сервиса; 6-я попытка логина за минуту блокируется rate-limit'ом; `screener -reset-password` сбрасывает пароль.
