# План разработки: от 0 до рабочего MVP

**Версия:** 1.3 · **Дата:** 08.07.2026
**Скоуп MVP:** Go-скринер + SQLite + REST API + React-фронтенд. **Hermes Agent и Telegram — вне MVP** (пост-MVP фаза, каркас под них закладывается, но не реализуется).

**Изменения v1.3:** отказ от VPN — публичный HTTPS (встроенный autocert) + авторизация email/пароль с JWT (PRD 4.9): таблица `users` и bootstrap — Э6, auth-эндпоинты и middleware — Э7, экран входа — Э9, autocert — Э10.

**Изменения v1.2:** эталон дизайна фронтенда — HTML-мокап `Скринер для фьючерсного скальпера/Скринер.dc.html` (prompt_design_agent.md больше не используется); сроки пересчитаны под исполнение кодовым агентом — оценки в сессиях вместо дней, из заголовков этапов убраны дневные оценки.

**Изменения v1.1:** топ-20 вместо топ-10; приоритет данных Binance при наличии инструмента на обеих биржах; редактирование правил отбора из UI вошло в MVP (таблица `settings` — Э6, `/api/settings` — Э7, редактор — Э9); добавлены указания для кодового агента (git-дисциплина, общий пакет доменных типов, «эффективная конфигурация», запись фикстур).

Принцип нарезки: каждый этап — самостоятельный блок с чётким выходным артефактом и способом проверки. Этапы идут в порядке зависимостей; после этапов 1–8 бэкенд полностью рабочий и тестируется без фронта (curl/тесты), фронт подключается последним.

## Этап 0 — Каркас проекта

**Делаем:** `git init` + первый коммит (дальше — коммит по завершении каждого этапа с зелёными тестами), структура репозитория, go.mod, загрузка конфига, логирование, Makefile.

```
screener/
├── cmd/screener/main.go
├── internal/
│   ├── domain/        # общие типы: Instrument, Ticker, Kline, MetricsRow, Settings
│   ├── config/        # YAML-конфиг: пороги, веса, интервалы, blacklist; effective-конфиг
│   ├── exchange/      # binance/, bybit/ — клиенты (Э1)
│   ├── normalize/     # нормализация символов (Э2)
│   ├── metrics/       # метрики, фильтры, инплей (Э3)
│   ├── scoring/       # скоринг и топ-N (Э4)
│   ├── corr/          # корреляция с BTC (Э5)
│   ├── store/         # SQLite (Э6)
│   ├── api/           # HTTP-хендлеры (Э7)
│   └── scheduler/     # циклы опроса (Э8)
├── web/               # React-фронт (Э9)
├── config.example.yaml
└── Makefile           # build, test, test-integration, run, lint
```

Технические решения (зафиксированы ресёрчем):
- Go 1.22+, роутер — стандартный `net/http` (методы и path-параметры уже в stdlib), внешний роутер не нужен.
- Конфиг — YAML (`gopkg.in/yaml.v3`), один файл, путь через флаг `-config`.
- Логи — stdlib `log/slog`, JSON-хендлер (удобно для journalctl).
- В конфиге сразу заводим все пороги методички: `min_volume_usd`, `min_change_pct` (20), `corr_threshold` (0.8), веса скоринга, `top_n` (20), blacklist, интервалы циклов; плюс поля деплоя/авторизации: `domain`, `listen_https`/`listen_http` (и dev-режим plain HTTP на localhost), `db_path`, `auth.bootstrap_email`/`auth.bootstrap_password` — имена этих полей используются в Deploy_VPS_guide.md, менять их нельзя без правки инструкции.
- Пакет `internal/domain` с общими типами (`Instrument`, `Ticker`, `Kline`, `MetricsRow`, `Settings`): все остальные пакеты зависят от него, а не друг от друга — исключает циклические импорты и переделку контрактов между этапами.
- Понятие «эффективной конфигурации» закладывается сразу: `config.Effective(yamlDefaults, dbOverrides)` — YAML-дефолты + рантайм-оверрайды правил отбора. До Э6 оверрайды просто пустые; в Э6 они подключатся из таблицы `settings`, в Э7 — начнут меняться через API. Это избавляет от рефакторинга сигнатур в середине проекта.

**Готово, когда:** `make build` собирает пустой бинарник, `make test` зелёный, конфиг-пример парсится, `./screener -config config.yaml` стартует и логирует загруженные настройки.

## Этап 1 — Клиенты бирж

**Делаем:** два независимых пакета `exchange/binance` и `exchange/bybit`, только публичные маркет-данные, без ключей.

Binance USDⓈ-M (`fapi.binance.com`):
- `GET /fapi/v1/exchangeInfo` — контракты, статусы, tickSize, baseAsset;
- `GET /fapi/v1/ticker/24hr` — вся суточная статистика одним запросом;
- `GET /fapi/v1/premiumIndex` — funding по всем символам;
- `GET /fapi/v1/klines` — свечи (понадобится в Э5).

Bybit v5 (`api.bybit.com`, category=linear):
- `GET /v5/market/instruments-info` — **с cursor-пагинацией** (символов >500, дефолтный лимит 500 — без пагинации потеряем половину рынка);
- `GET /v5/market/tickers` — цена, turnover24h, funding, OI, Δ24h;
- `GET /v5/market/kline` (limit до 1000 — неделя часовиков в один запрос).

Общее для обоих клиентов: таймауты (5–10 с), retry с экспоненциальным backoff (3 попытки), обработка кодов лимитов (Bybit retCode 10006 + заголовки `X-Bapi-Limit-*`; Binance — заголовок `X-MBX-USED-WEIGHT-1M`, бюджет 2400/мин), единый интерфейс `Ticker`/`Kline` структур на выходе.

**Тестируем:**
- Юнит: фикстуры — записанные реальные JSON-ответы в `testdata/`, поднимаем `httptest.Server`, проверяем парсинг, пагинацию Bybit (фикстура с cursor на 2 страницы), ретраи (сервер отдаёт 500 → 200). Фикстуры записываются один раз curl-скриптом (`make fixtures` или задокументированные в README команды) — чтобы их можно было переснять при изменении схем ответов бирж.
- Интеграционный smoke (`go test -tags=integration`): живой запрос к каждому эндпоинту, проверка «вернулось >N символов, поля не нулевые». Гоняется вручную, не в CI.

**Готово, когда:** оба клиента возвращают полный список тикеров с реальных API, пагинация Bybit отдаёт все ~600+ символов.

## Этап 2 — Нормализация символов

**Делаем:** пакет `normalize` — сведение `1000PEPEUSDT` (Binance) и `PEPEUSDT` (Bybit) к единому инструменту `{base: PEPE, multiplier: 1000}`; выделение квотируемой валюты (USDT/USDC); фильтр стейбл-пар; флаги `on_binance` / `on_bybit` (из них выводится «есть только на Bybit» — по методичке это интересные листинги).

Правила: префиксы 10/100/1000/10000/1000000 перед известным base; при коллизиях — явная таблица исключений в конфиге; неизвестный паттерн → warning в лог (позже станет алертом).

**Тестируем:** табличный юнит-тест на 20+ кейсов: `1000PEPEUSDT`→PEPE×1000, `BTCUSDT`→BTC×1, `1000SHIBUSDT`, `SHIB1000USDT` (бай-битовский вариант написания), USDC-пары, стейблы (`USDCUSDT` — отсев), мусорные символы.

**Готово, когда:** объединённый список с двух бирж дедуплицирован, у каждого инструмента корректные флаги бирж и множитель.

## Этап 3 — Метрики и фильтры

**Делаем:** пакет `metrics` — чистые функции над данными Э1/Э2, без I/O.

Метрики на инструмент: диапазон дня `(high−low)/low %`; изменение 24ч %; оборот 24ч $ (сумма по биржам); funding; относительный tickSize. **Приоритет данных Binance:** если инструмент есть на обеих биржах, ценовые метрики (Δ24ч, диапазон, funding, tickSize) берутся из данных Binance, Bybit участвует только в сумме оборота; для инструментов без Binance — данные Bybit. Плюс **инплей** — отклонение Δ24h инструмента от медианного Δ24h по рынку (формализация правила методички про памп всего рынка: `is_inplay = растёт кратно сильнее медианы ИЛИ падает при растущей медиане`, кратность — в конфиге, дефолт ×2 и порог рынка +3%).

Жёсткие фильтры (методичка + здравый смысл): статус Trading; не стейбл-пара; не в blacklist; `оборот ≥ min_volume_usd` (дефолт $100M — калибруется); опциональный фильтр `|Δ24h| ≥ min_change_pct` (дефолт 20%, по методичке; выключаемый — иначе в спокойные дни топ пустой, при выключении просто ранжируем по score).

**Тестируем:** юнит на синтетике — рукотворный набор из 10 инструментов с известными значениями, проверяем каждую метрику числом, каждый фильтр — кто прошёл/не прошёл; отдельные кейсы на инплей (рынок +30%, монета +65% → inplay; монета −5% на рынке +30% → inplay; монета +32% → не inplay); кейс приоритета источника: инструмент на обеих биржах с разными Δ24ч → в метриках значение Binance, оборот — сумма двух бирж.

**Готово, когда:** на живых данных функция возвращает отфильтрованный список с метриками и лог «просканировано X → прошли Y».

## Этап 4 — Скоринг и топ

**Делаем:** пакет `scoring` — перцентильная нормировка каждой метрики по текущей выборке (устойчива к выбросам), взвешенная сумма `score = w_vol·волатильность + w_turn·оборот + w_inplay·инплей − w_corr·корреляция` (веса из конфига, корреляция подключится в Э5 — до этого её вес просто 0), сортировка, топ-N.

**Тестируем:** юнит: при весах (1,0,0,0) порядок совпадает с сортировкой по волатильности; изменение весов меняет порядок предсказуемо; стабильность при равных значениях (tie-break по обороту).

**Готово, когда:** `screener -once` печатает в stdout осмысленный топ-20 с реального рынка. **Это первая точка полезности проекта** — уже можно глазами сверять с методичкой и калибровать пороги.

## Этап 5 — Корреляция с BTC

**Делаем:** пакет `corr`:
- загрузка 1h-свечей за 7 дней (168 точек) по каждому инструменту + BTCUSDT: свечи берутся с Binance, если инструмент там торгуется (приоритет данных Binance), иначе с Bybit; BTCUSDT — той же биржи, что и свечи инструмента;
- выравнивание рядов по open time (точки без пары отбрасываются в обеих сериях);
- доходности `r[i] = close[i]/close[i−1] − 1`, Пирсон по формуле;
- если валидных точек < 100 (свежий листинг) → `null`, не 0;
- результат — `btc_corr_7d ∈ [−1..1] | null` и флаг `high_corr = corr > corr_threshold` (красное подчёркивание из методички).

Бюджет запросов: Binance klines (limit≤499) = weight 2, ~600 символов ≈ 1200 weight при лимите 2400/мин — проходит, но качаем пачками по 50 с паузой (запас ×3); Bybit — просто спред запросов во времени. Полный пересчёт занимает единицы минут и выполняется редко (Э8).

**Тестируем:** юнит на эталонах: corr(x, x)=1.0, corr(x, −x)=−1.0, независимый шум → |corr|<0.2 (сид фиксирован); тест выравнивания: ряды со сдвигом и дырками дают корректный результат; тест «мало точек → null». Ручная проверка на живых данных: у мажоров-«прилипал» (SOL, DOGE, XRP) corr ожидаемо >0.7, у свежего мемкоина в пампе — заметно ниже.

**Готово, когда:** у инструментов из топа появляется колонка корреляции, значения проходят санити-чек против методички.

## Этап 6 — Хранилище SQLite

**Делаем:** пакет `store` на `modernc.org/sqlite` (pure Go, CGO_ENABLED=0).

Обвязка по продовым практикам драйвера: `PRAGMA journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`; **два пула** — writer с `SetMaxOpenConns(1)` и отдельный reader (иначе при конкурентной записи ловится SQLITE_BUSY); версия `modernc.org/libc` в go.mod — строго та же, что в go.mod драйвера.

Схема (миграции — нумерованные .sql в `go:embed`, применяются на старте): `instruments` (base, multiplier, символы бирж, флаги), `prop_instruments`, `snapshots`, `snapshot_rows` (метрики + score + rank + btc_corr_7d + is_inplay + in_prop_list), `corr_cache` (instrument_id, corr, updated_at), `settings` (key, value, updated_at) — рантайм-оверрайды правил отбора, подключаются к `config.Effective` из Э0, `users` (id, email UNIQUE, password_hash, created_at) + bootstrap-логика: при пустой таблице создаётся пользователь из конфига (bcrypt-хэш, пароль в БД не попадает).

**Тестируем:** юнит на временной БД (`t.TempDir()`): миграции с нуля и повторный запуск (идемпотентность); запись/чтение снапшота — round-trip всех полей; CRUD проп-листа; CRUD настроек + round-trip эффективной конфигурации (оверрайд перекрывает YAML-дефолт, удаление оверрайда возвращает дефолт); bootstrap пользователя идемпотентен (повторный старт не перетирает учётку); конкурентный тест — параллельные читатели во время записи не получают BUSY.

**Готово, когда:** снапшот из Э4 сохраняется и читается, файл БД переживает рестарт.

## Этап 7 — REST API

**Делаем:** пакет `api` поверх store:

| Метод | Путь | Что |
|---|---|---|
| GET | `/api/top?limit=10` | текущий топ (последний снапшот) |
| GET | `/api/top?format=text` | текст-версия (задел под будущего агента) |
| GET | `/api/history?symbol=&days=` | история по инструменту |
| GET | `/api/snapshots?from=&to=` | список снапшотов, топ-3 каждого |
| GET | `/api/stats?days=` | агрегаты для страницы «История» (частотность, доля пропа, новички) |
| GET/PUT | `/api/prop-list` | проп-лист |
| GET/PUT | `/api/settings` | правила отбора: пороги, веса, top_n; валидация диапазонов, невалидный набор отклоняется целиком (400) |
| POST | `/api/refresh` | форс-пересчёт (быстрый цикл) |
| GET | `/api/health` | статусы бирж, время последнего снапшота, возраст corr-кэша |
| POST | `/api/auth/login` | email+пароль → JWT в HttpOnly Secure cookie (30 дней); rate-limit 5/мин с IP |
| POST | `/api/auth/logout` | очистка cookie |
| GET | `/api/auth/me` | текущий пользователь (проверка сессии для UI) |

Плюс: JWT-middleware на все `/api/*`, кроме `/api/auth/login` и `/api/health` (HS256, секрет генерируется при первом старте и хранится в data-каталоге); bcrypt-проверка пароля; CLI-флаг `-reset-password` (пересоздаёт пароль из bootstrap-полей конфига); graceful shutdown; JSON-ошибки единого формата; CORS для dev-режима фронта.

**Тестируем:** `net/http/httptest` на каждый хендлер с подготовленной БД (happy path + невалидные параметры + пустая БД); для `/api/settings` — валидные значения сохраняются и видны в GET, невалидные (отрицательный объём, corr > 1) → 400 без частичного применения; авторизация: login с верным паролем → 200 + cookie, с неверным → 401; защищённый эндпоинт без cookie → 401, с cookie → 200; 6-я попытка логина за минуту → 429; ручной smoke-чеклист curl-команд в README.

**Готово, когда:** весь контракт отвечает корректным JSON, `/api/health` честно показывает деградацию (выключаем сеть — статус биржи падает).

## Этап 8 — Оркестрация циклов

**Делаем:** пакет `scheduler` — связывает всё:
- **быстрый цикл** (каждые 15 мин, конфиг): чтение эффективной конфигурации (YAML + `settings` из БД — правки настроек применяются без рестарта) → тикеры → нормализация → метрики → фильтры → скоринг (с корреляцией из кэша) → снапшот в БД;
- **медленный цикл** (каждые 2 ч, конфиг): пересчёт корреляций пачками → corr_cache;
- `POST /api/refresh` триггерит быстрый цикл вне расписания (mutex от параллельных прогонов);
- при недоступности одной биржи цикл не падает: снапшот собирается по живой бирже, health отражает деградацию;
- graceful shutdown по SIGTERM (дожидаемся конца текущего прогона).

**Тестируем:** юнит с инжектируемыми часами/интервалами на срабатывание и mutex; **сквозной интеграционный тест бинарника**: старт с тестовым конфигом (интервал 5 с) → ждём снапшот → `GET /api/top` возвращает непустой топ → SIGTERM завершает чисто. Это главный тест этапа — после него бэкенд считается рабочим.

**Готово, когда:** бинарник живёт часами, снапшоты копятся, refresh работает, падение Bybit не роняет процесс.

## Этап 9 — Фронтенд

**Эталон дизайна:** готовый HTML-мокап `Скринер для фьючерсного скальпера/Скринер.dc.html` + скриншоты в `shots/`. Это самодостаточная вёрстка с полной темизацией (IBM Plex Sans/Mono, светлая и тёмная темы на CSS-переменных: `--bg`, `--surface`, `--accent`, `--pos`/`--neg`, `--warn-*` и т.д.). Дизайн переносится в React максимально точно: CSS-переменные, шрифты, цвета, отступы, бейджи и структура блоков берутся из мокапа как есть, ничего не изобретаем.

**Делаем:** `web/` — Vite + React, три страницы по мокапу: «Топ» (статусная строка, 4 сводные карточки, таблица с раскрывающимися строками, поиск/фильтр биржи/«только проп», кнопка обновления), «История» (частотность, инсайт-карточки, список снапшотов, селектор периода), «Настройки» (редактор проп-листа + редактор правил отбора: мин. оборот, мин. % движения и вкл/выкл этого фильтра, порог корреляции, параметры инплея, веса скоринга, размер топа; валидация на форме, «Сбросить к дефолтам», подпись «применится со следующим снапшотом»). Переключатель светлой/тёмной темы (дефолт — системная). В таблице топа — колонки/бейджи новых метрик: corr (с подсветкой `high_corr`), инплей, «только Bybit». Плюс экран входа (email+пароль, в стилистике мокапа): все fetch — с credentials, глобальная обработка 401 → редирект на логин, кнопка выхода в шапке.

Dev-режим: `vite dev` с proxy `/api` → `localhost:8080` — фронт разрабатывается против живого бэкенда из Э8.

**Тестируем:** визуальная сверка каждой страницы с мокапом и скриншотами `shots/` (обе темы); ручной чеклист по каждой странице (данные соответствуют curl-ответам API; тема переключается и переживает переход между страницами; мобильная ширина — таблица сворачивает второстепенные колонки; состояния: пустая БД, ошибка API, деградация биржи из health). `npm run build` собирается без ошибок.

**Готово, когда:** все три страницы работают против реального бэкенда в dev-режиме.

## Этап 10 — Сборка и деплой

**Делаем:** `//go:embed web/dist` — статика внутри бинарника (SPA-fallback на index.html); HTTPS — встроенный autocert: слушаем `:443` (TLS) и `:80` (редирект на HTTPS + ACME-challenge), кэш сертификатов в data-каталоге, dev-режим — plain HTTP на localhost без домена; `make release`: `npm run build` → `CGO_ENABLED=0 GOOS=linux go build`. Сам деплой на VPS выполняется **вручную владельцем** по пошаговой инструкции **Deploy_VPS_guide.md** (домен+DNS, systemd, бэкапы, обновление/откат, сброс пароля, диагностика) — задача агента на этом этапе: `make release` работает, бинарник самодостаточен, инструкция соответствует собранному артефакту (имя бинарника, флаги `-config`/`-reset-password`, поля конфига `domain`, `listen_https`/`listen_http`, `db_path`, `auth.bootstrap_*`).

**Тестируем (= приёмка MVP):**
1. Открыл `https://домен` с ноутбука и телефона из обычной сети: сертификат валиден, HTTP редиректит на HTTPS, без логина — экран входа, после логина топ отображается, тема работает.
2. `systemctl restart` и полный ребут VPS — сервис поднялся сам, история цела.
3. 48 часов наблюдения: снапшоты каждые 15 мин без пропусков, corr обновляется, память процесса стабильна (<100 МБ).
4. Санити методички: в топе нет монет с оборотом ниже порога; «прилипалы» (SOL/DOGE/XRP при corr>0.8) помечены; инплей-флаг срабатывает в дни общего пампа.
5. Правка порога объёма или процента из UI меняет выборку со следующего снапшота (или по «Обновить сейчас»); «Сбросить к дефолтам» возвращает YAML-значения; настройки переживают рестарт.
6. Авторизация: без cookie `/api/top` отвечает 401; сессия переживает `systemctl restart`; rate-limit логина срабатывает; `screener -reset-password` восстанавливает доступ.

## Сводка по срокам

Код пишет агент — чистое время написания измеряется часами, а не днями. Оценки даны в **сессиях**: «агент делает блок → человек проверяет контрольную точку». Узкое место не код, а проверки на живом рынке и календарное время приёмки.

| Блок | Объём | Проверка человеком на выходе |
|---|---|---|
| Э0–Э2 каркас, клиенты бирж, нормализация | 1 сессия | тесты зелёные, оба клиента отдают живые тикеры |
| Э3–Э4 метрики, фильтры, скоринг | 1 сессия | **главная ручная точка:** сверка консольного топ-20 с методичкой, калибровка порогов |
| Э5–Э6 корреляция BTC, SQLite | 1 сессия | санити corr на «прилипалах» (SOL/DOGE/XRP > 0.7) |
| Э7–Э8 REST API + авторизация, оркестрация | 1–2 сессии | curl-смоук (включая логин и 401 без cookie), наблюдение 2–3 циклов подряд |
| Э9 фронтенд | 1–2 сессии | визуальная сверка с мокапом (обе темы), мобильная ширина |
| Э10 деплой | 1 сессия | сервис поднялся на VPS, HTTPS-сертификат выпустился, логин работает |
| **Итого** | **~7–8 сессий, ~2 календарных дня активной работы** | + 48 ч финального наблюдения |

Что агентом **не ускоряется** (календарное время): 48-часовая приёмка стабильности; калибровка порогов — нужны реальные рыночные дни; проверка инплей-флага — нужен день общего пампа рынка (проверяется по мере появления, не блокирует релиз).

Контрольные точки полезности: после Э4 — консольный топ для ручной сверки с методичкой; после Э8 — рабочий API (можно смотреть curl'ом); после Э10 — полный MVP.
